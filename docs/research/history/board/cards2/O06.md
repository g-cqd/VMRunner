## Built so far: the console client filters the guest's output, 2026-10-23

- `ConsoleOutputFilter` (in `GuestConsole`): a streaming filter for what a guest prints, its state kept between reads and
  bounded (a CSI sequence of at most 256 bytes, a control string given up after 4 KiB, then text again). It passes text,
  well-formed UTF-8, line feed, carriage return, tab, backspace and the bell, and the CSI sequences a boot log, a login
  prompt and a shell's line editing use: colours and attributes, cursor movement, erasing in the line or the display (not
  the scrollback), inserting, deleting and erasing characters. It removes, whole, window titles, the clipboard,
  hyperlinks, every query that makes the terminal answer, every mode change, resets, C1 controls in both forms and every
  other sequence or control string.
- `vmr guest console` filters by default; `--raw` passes the guest's output unchanged after a warning on standard error.
  The filter is on the client's relay only: the bridge and `ConsoleSession` still see the raw bytes, which the exec
  markers and the prompt detection need.
- The client puts the terminal back however the session ends: its settings after a detach, the end of input, an error,
  or SIGHUP, SIGINT, SIGQUIT, SIGPIPE or SIGTERM (received through dispatch sources, so no code runs in signal context;
  exit status 128 plus the signal); a colour reset after a filtered session, and after a raw one the modes a guest's
  programs most often leave on. A crash of the client itself is not covered: `stty sane` restores the terminal.
- Tested with a table of 123 sequences (each also cut at every byte), random input, a hand-written boot and login log,
  the relay on socket pairs, raw mode on a pseudo-terminal pair and a signal sent to the test process. Not yet tried in a
  terminal application, nor against a real guest.

# Diary — 2026-10-23 (NN)

## The console client filters the guest's output and puts the terminal back

Six commits (five of code and tests, one of documentation) make `vmr guest console` safe to point at an untrusted guest;
each passed `swift run vmr check`. Until now the client copied everything the guest printed to the person's terminal, so
a guest could set the window title, write or query the clipboard, make the terminal type answers into the person's input,
switch on modes that stayed on after the session, or reset the terminal; and a signal left the terminal raw. Nothing here
ran against a real guest or in a terminal application: the claims below come from tests on socket pairs, pipes and a
pseudo-terminal pair.

| # | Claim | Probe | Verdict |
|---|---|---|---|
| 1 | Titles, the clipboard (write and query), hyperlinks, palette changes, every query that makes a terminal answer, mode changes, resets and C1 controls in both forms are removed whole, leaving no character behind | a table of 85 such sequences between two letters, and all of them in one stream | TESTED |
| 2 | Text, UTF-8, LF, CR, tab, backspace, the bell, colours, cursor movement, erasing (not the scrollback) and character editing pass unchanged | 30 kept rows and a hand-written boot and login log | TESTED |
| 3 | A sequence or a character cut between two reads gives the same output | every row cut at every byte and fed a byte at a time; the relay's own 16 KiB boundary | TESTED |
| 4 | The filter's state is bounded and it reads text again after a control string with no end | the 256-byte and 4 KiB limits at, one short of and far past them | TESTED |
| 5 | Random input never gets a forbidden byte through, never grows, and filtering twice changes nothing | 500 seeded random inputs | TESTED |
| 6 | The bridge and the exec path still see raw bytes | the filter is only in the client's relay; the console's existing tests pass unchanged | INFERRED (from the call graph; the existing console suites still pass) |
| 7 | Raw mode is undone after a normal return and after a thrown error | a pseudo-terminal pair | TESTED |
| 8 | A watched signal ends the session through the normal path instead of killing the process | a signal sent to the test process becomes a byte on the watch's pipe; the relay ends on that byte | TESTED in parts; the whole path with a real terminal NOT RUN |
| 9 | A real terminal application shows no title change, no clipboard change and no answer typed after a hostile guest's output | the owner's run | NOT RUN |

### What was built

- `ConsoleOutputFilter` in `GuestConsole`, used by `ConsoleRelay` on the console-to-terminal direction only.
- `vmr guest console`: filtered by default, `--raw` with a warning, the terminal's settings restored on a signal, colours
  (or, after `--raw`, the usual modes) reset at the end; its help says all of it.
- `SignalWatch` and `TerminalMode.raw(on:)` in the tooling.

### Decisions to confirm

The defaults the owner may change: the allow-list (colours, cursor movement, erasing in the line and display, character
editing; no alternate screen, no scroll region, no saving of the cursor); the bell passes; malformed UTF-8 is dropped
rather than shown as a replacement character, so the output never grows; a single C1 byte is dropped alone while a C1 in

- `vmr guest exec` prints the command's output unfiltered (ADR-0052, decision 8): a hostile guest can still reach the terminal
  through it. Only the console client is covered.

The tests close every descriptor they open and remove nothing else; no scratch folder is used.
