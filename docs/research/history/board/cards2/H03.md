# H03 — A separate-preferences run leaves the sidebar width alone in the owner's preferences

Model: haiku · Effort: low · Worktree: yes, `WT = ~/Developer/g-cqd/VMRunner-chains/h-macos` (branch `chain/h-macos`, created from `main` at `471c681`) · Chain: H
Read `cards/COMMON.md` first. Anchors: locate every edit by its text (`grep -nF`), never by a line number. One commit, signed, atomic; `swift run vmr check` 8/8 before it. No board ids, no outside project names in code, docs, comments or commit messages.


Why (same run): with `VMRUNNER_DATA_DIR` set (`PreferencesDomain.isSeparate`) the run changed the owner's `com.example.VMRunner` domain: the main window's split-view entry (`NSSplitView Subview Frames ...`) now marks the sidebar collapsed, so the owner's next normal launch can open with the sidebar hidden. `ContentView.swift`'s `WindowObservingView` already calls `stopSavingFrameAndState()` (frame autosave name cleared, not restorable) on the window, but the `NavigationSplitView`'s own `NSSplitView` keeps an autosave name and writes to the standard domain. How it got collapsed in a run that only pressed Resume Setup and Force Stop is not known; the autosave is the one writer found.

- **Files:** `Sources/VMRunner/Views/ContentView.swift` (`WindowObservingView`, `NSWindow.stopSavingFrameAndState`), `Sources/VMRunner/Model/PreferencesDomain.swift` (doc comment), `Tests/VMRunnerTests/` (a test on the helper below), `docs/diary` entry is written by card H04, not here.

## Change
1. Add to `ContentView.swift` an extension `NSView { func stopSavingSplitViewState() }` that walks the view tree (`subviews`, depth-first) and sets `autosaveName = nil` on every `NSSplitView` found (the property is `NSSplitView.AutosaveName?`; if the SDK type requires, assign `""`). Keep it small; no recursion limit issue (the tree is shallow).
2. Call it from `NSWindow.stopSavingFrameAndState()` on `contentView`, and ALSO once more on the next main-actor turn (`Task { @MainActor in ... }`, one hop) because SwiftUI creates the split view after the window exists; both only when `PreferencesDomain.isSeparate` (the call site already checks it). The `window` of `WindowObservingView` is `unowned(unsafe)`: capture the window strongly into the task as a local `let` before the hop.
3. `PreferencesDomain.isSeparate` doc comment: also say the split view's saved widths are not recorded.
4. Test: build an `NSView` with a nested `NSSplitView` whose `autosaveName = "x"`, call the helper, expect `autosaveName` nil/empty on it and on a split view two levels deeper. Document in the commit body that the full effect (the standard domain staying untouched during a real run) is owner-verifiable only: run with `VMRUNNER_DATA_DIR=/tmp/x`, then `defaults read com.example.VMRunner | grep -c "NSSplitView"` unchanged.
