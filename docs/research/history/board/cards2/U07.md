## Decisions (read before editing; each is written so a reviewer can disagree with it)

1. **What the editor shows a Windows machine.** General, security, compute (processors, memory, nested virtualization where the host can do it), storage (a disk that grows, caching, flushing, extra disks), installer (the ISO, the attach switch, and the driver disc), display (resolution, follow the window), input (keyboard capture; the pointer is the USB one), audio, network (with the note that Windows has no built-in driver for the network device), identity, devices (balloon, entropy, vsock), agent access, shared folders, host information and snapshots. **Hidden for Windows:** provisioning, the first-boot section, the serial-console row, Rosetta and the clipboard agent, the graphics device choice, pixel density and pixels per point, the pointing-device choice, the disk-interface choice, Secure Boot, and the "Allow suspend" switch. Every hidden row is one the model already refuses for Windows (`validate()`) or one that does nothing for it.
2. **Shared folders and host information are shown, with a note, not hidden.** Both reach a guest through the shared virtio file-system device, which a Windows guest sees only with a driver of its own. Hiding them would take away a feature an owner who installs that driver can use, and the exposure summary lists them either way, so the editor shows them and says in one line (`WindowsRequirements.sharingNote`) that the guest needs a driver. The mount-command hint, which names a Linux or macOS command, is replaced by that note.
3. **Snapshots stay.** A snapshot is a copy-on-write clone of the stopped machine's disk and firmware variables (`takeSnapshot`); it writes no memory, so it is not suspend, and it works for a Windows machine as for a Linux one. Only the suspend switch is hidden (`guestSuspendReason` already makes the controller report that suspend is unavailable).
4. **The driver disc** is chosen in the installer section with its own picker target; a file inside the Machines folder is refused with the same alert an extra disk gets, and the grant is `HostPathGrant(.driverDisc, path, writable: false)`, so the machine reads as approved. "Remove Driver Disc" clears the path.
5. **Nested virtualization** is a row for every generic-platform guest (Linux and Windows); the Windows caption is "Lets the guest run its own hypervisor." (the Linux one names `/dev/kvm`).
6. **The audit of `Security.swift`'s comparisons of the guest with `.linux` or `.macOS`.** Nine expressions remain after the builder card (the `let linux` of the posture serves five rows). Each was decided for a Windows machine:

| Expression | Windows today | Decision |
|---|---|---|
| `secureBootAvailability`: `guard guest == .linux else { .notApplicable }` | no Secure Boot switch; the builder passes `secureBoot: false` | KEPT |
| posture `linux && sharesClipboard` and exposure `guest == .linux, sharesClipboard` | the clipboard agent is Linux-only; a Windows machine's setting is inert (the Standard profile sets it on every guest) | KEPT: no clipboard row for Windows, pinned by a test |
| posture `linux && rosetta`, exposure `guest == .linux, rosetta` | `validate()` refuses it | KEPT, pinned |
| posture `linux && serialConsole`, exposure `guest == .linux, serialConsole` | `validate()` refuses it; the builder makes no console | KEPT, pinned |
| posture `linux && !provisioningSpecPath.isEmpty`, `linux && secureBoot` | refused by `validate()` | KEPT, pinned |
| posture `provisioned` (`guest == .macOS && ...`), `recovery`, exposure first-boot account lines | macOS-only | KEPT, pinned |
| exposure `if guest == .linux { items.append(secureBootExposure) }` | a Windows machine always boots with Secure Boot off, and the summary said nothing about it | **CHANGED** to `guest.usesGenericPlatform`: the line "Secure Boot is off: unsigned bootloaders and kernels can run." appears for Windows as it does for Linux with the switch off (macOS has no such line) |

7. **One addition the task did not list: a warning under the profile picker.** A Windows machine under the Isolated or Hardened profile cannot start (the profile closes private interfaces and the machine needs one, card 3). The summary list already says "Private interface: ...", but nothing told the person that the profile stops the machine. `WindowsRequirements.profileNote(for:)` gives the sentence, shown in orange under the profile summary for a Windows machine whose detected profile closes private interfaces; a test pins it. It is a text row only.
8. **Help.** A topic `windowsMachines` (area "Getting started") holds the six requirement statements verbatim (it reads `WindowsRequirements.lines`, so the help and the sheet cannot drift), what the sheet takes (a local installer, the optional expected SHA-256, the driver disc), the defaults, and a pointer to Private interfaces. The three sentences that said Windows is unsupported are rewritten (guest systems, Linux images, Limits); the overview, the installer, nested-virtualization and suspend topics, and the Isolated line of the profiles topic now include Windows or the driver disc; `WindowsStartsWithoutPMU` is documented, developer-only, beside `DisablePrivateInterfaces` in the Private interfaces topic. A test says no help text still says Windows is unsupported, and that no help text that mentions Windows contains "bypass", "LabConfig", "autounattend", "unattend", "BypassTPM" or "registry".
