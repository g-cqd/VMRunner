Why: Windows on ARM is to run in the app (chain U), and the later cards add a machine builder for it, a New Machine preset and editor sections. All of them need `GuestOS` to have a third value, and every place that today answers "macOS or else Linux" must be looked at first, because a third value would silently take the "else" branch and be treated as Linux. This card adds `GuestOS.windows`, reads and writes it, gives a new Windows config its defaults and a disk range, refuses the Linux-only features on it, and goes through every guest-dependent place in `Sources/` (the audit below): each is either changed to answer for Windows on purpose, or kept after a decision that is written down. Where the answer belongs to a later card (the builder, the New Machine preset, the editor sections) the case is explicit and fails safe: the builder and the provisioner throw a typed error, the New Machine sheet cannot create a Windows machine and does not offer one. No behaviour changes for macOS and Linux machines.

## Names later cards rely on

- `GuestOS.windows` (raw value `"windows"`, label `Windows`, symbol `pc`); `GuestOS.newMachineChoices` (`[.macOS, .linux]`, what the New Machine guest picker iterates: the preset card adds `.windows` to this list and nowhere else); `GuestOS.usesGenericPlatform` (true for Linux and Windows: generic platform, EFI firmware, virtio graphics).
- The typed error to replace: `SetupError.unsupportedGuest(GuestOS)` (`Engine/SetupError.swift`), thrown for `.windows` in two places, `ConfigurationBuilder.build` (its `switch config.guest`) and `Provisioner.run`. The builder card replaces the first `case .windows: throw SetupError.unsupportedGuest(config.guest)` by a call to its `configureWindows` and keeps the error case (the provisioner still throws it until a Windows setup exists); its text is "This version of VMRunner can't start Windows machines.".
- Defaults: `VMConfig.new(name:guest:)` (unchanged signature) now forwards to `VMConfig.new(name:guest:hostCPUs:hostMemoryGiB:)`, the pure function tests use; for `.windows` it gives 4 processors and 8192 MiB on a host with at least 8 processors and 16 GiB (half the host's on a smaller one, never below 2 processors and 2 GiB), `diskGiB` 64, `diskInterface` `.nvme`, `networkMode` `.nat`, display 1920x1200, `gpu` `.apple`, `audioOutput` and `audioInput` off, `serialConsole` off, `rosetta` off, `secureBoot` off, `sharesClipboard` off, `pointingDevice` `.mouse`, no provisioning spec, no installer.
- `EditorLimits.newWindowsDiskGiB` (`64...2048`) and `EditorLimits.newDiskGiB(for:)` (now a `switch`).
- `VMConfig.privateCapabilities` is `[.performanceMonitoringEmulation]` for Windows (its exposure line shows; the builder card reads the property's meaning from the policy card's interface).
- `VMConfig.usesNVMeMainDisk` (Linux or Windows with `diskInterface == .nvme`; the builder's main disk and the saved-state comparison use it), `VMConfig.guestSuspendReason` (non-nil for Windows), `VMConfig.attachedInstallerPath` (now also Windows: the installer ISO attached as a read-only USB drive by the shared `ConfigurationBuilder.storage(for:bundle:)`).
- `VMConfig.validate()` refuses on a Windows config: `gpu` other than `apple`, `rosetta`, `nestedVirtualization`, `serialConsole`, `secureBoot`, and a non-empty `provisioningSpecPath`, each with `"<key> is not available for a Windows machine"` (private `validateGuest()`); a later card that needs one of them on Windows removes its line there.
