## Why

A Linux machine follows its window: `DisplayFollower` (the policy) asks its display for the size of the view at `scale` pixels per point. For the framework's device the display is a `VZGraphicsDisplay`. This card gives the custom GPU a display the policy can drive, and wires it into the window of the previous card.

**The adapter.** `CustomGPUResizableDisplay: ResizableDisplay` over a `CustomDisplaySource`:
- `reconfigure(sizeInPixels:)` takes a size of whole pixels (anything else, negative, fractional, not a number, past 32 bits, throws without asking the device) and asks the source for it (`requestDisplaySize`), which asks the device: the device's state takes the size if the library allows it (`GPULimits.allowsDisplay`: no zero side, none above 8192, a picture of it within one resource) and the next `GET_DISPLAY_INFO` then answers with it. The device refuses what it cannot report and the adapter throws, so the follower reports a refusal and retries as it does for the framework.
- `sizeInPixels` is the size of the picture the guest last drew, and the size the machine started with before its first picture. It is **not** the size that was asked for: the guest has not changed its display until it draws at the new size, as with the framework's display, and a follower that read the requested size back would take every request for answered and never ask again.
- `observeReconfigurationEnd` fires when the guest first flushes a picture **of the size that was asked for**, once per request. That is all the device sees of a guest using a size (a flush; setting a scanout or creating a resource come earlier but carry no pictures). It is reported through `CustomScreen.observeFrames`, which calls its observers with the size of every picture the guest flushes before the screen decides whether to draw it; the registration is a token the follower holds, and the screen keeps its observers weakly.

**The window.** `CustomGPUDisplay` gets a coordinator, the same `DisplayResizer` as the framework's display, and passes the container's size to it; `DisplayResizer.configure(source:scale:enabled:holdFor:guestAnswered:)` makes the follower with the adapter as its display (the machine's setting `followsWindow` and the 10-second firmware hold at a cold boot behave as for the framework's device). The firmware hold exists because the firmware reads the display once, early; whether the firmware's driver for this device does is unknown (no guest run).

**The event bit.** T05 left open that the display event is never cleared (the guest's write to `events_clear` never reaches the host) and that a second update with the same bytes might not interrupt the guest. Decision: `GPUConfigSpace.displayChange` is two spaces, the event **cleared**, then **set**, and the device writes both, in that order, for every resize. Every write after the first then differs from the one before it (the device starts with the event clear, so the first resize's cleared write repeats the start, and only its set write changes anything), which holds if the framework skips an update whose bytes did not change. A guest woken by the cleared write reads an event of zero and has nothing to handle (the spec's driver acts on the bit); one woken only by the set write handles it. The cost is one more update per resize, and the 0 ms measured for one update says an update is cheap. Whether this makes a second resize re-trigger the request is **left to the real run**; the roadmap says so.

**Judgement calls (recorded; do not change them):**

1. **`CustomGPUDevice.requestDisplaySize` is synchronous and no longer throws.** `ResizableDisplay.reconfigure` is synchronous and must refuse a size at once; the framework's `update` is asynchronous, so the device starts it in a main-actor task (`self` weak, one failure logged once as `Couldn't tell the guest the display changed`). The test of T05 that called the old asynchronous form (`aDisplaySizeOutsideTheLimitsIsRefusedWithoutAMachine`) is **deliberately edited**: `async throws` and the three `try await` are dropped, nothing else.
2. **A size the device cannot report is refused, not fitted.** The start size is fitted (T09, `fittingDisplay`) because the user chose nothing exact there, and a refusal at start would leave no machine; a resize to a size past one resource (more than 16 777 216 pixels, about 5.4K at 16:9: 64 MiB) is refused with the follower's usual report and retries, then waits for the next change of the window. A window that large on a 8K display therefore keeps the last size. Fitting it instead is possible and is not decided here.
3. **A guest that answers with another size** (its driver clamps) never fires the end; the follower reports it as ignoring the request and asks again after its growing delays, as it does when the framework's display never reaches the size.
4. **`DisplayResizer` for the custom device has no `DisplayTrace`** (that traces the framework's machine view). The container's layout diagnostics still run.
5. **`FakeCustomSource` records the sizes it is asked for** and can refuse them (a test-support file edited; no test changed). `CustomScreen.displaySize` becomes immutable (it was `private(set) var` and nothing set it).

````swift
import CoreGraphics

/// The custom GPU's display as `DisplayFollower` resizes it, in place of the framework's `VZGraphicsDisplay`.
///
/// - `sizeInPixels` is the size of the picture the guest last drew (the size the machine started with before its first), not the
///   size it was asked for: the guest has not changed its display until it draws at the new size, as the framework's display
///   does not either, and a follower that read the requested size back would take every request for answered.
/// - A request is passed to the device, which answers the guest's next display-information request with the new size and tells
///   the guest to ask for it. The device refuses a size it cannot report (zero, past its limits, a picture too big for one
///   resource), and so does this display; a size that is not whole pixels is refused before the device is asked.
/// - The end of a reconfiguration is the first picture the guest flushes at the size that was asked for, which is all the device
///   sees of the guest using a size (it sees no setting of the display by the framework). It is reported once per request.
@MainActor
final class CustomGPUResizableDisplay: ResizableDisplay {
    /// The device or the size refuses the request.
    struct Refused: Error {}

    private let source: any CustomDisplaySource
    /// The size of the last request, until the guest draws at it.
    private var awaited: CGSize?

    init(source: any CustomDisplaySource) {
        self.source = source
    }

    var sizeInPixels: CGSize { source.screen.pictureSize }

    func reconfigure(sizeInPixels size: CGSize) throws {
        guard let width = UInt32(exactly: size.width), let height = UInt32(exactly: size.height),
            source.requestDisplaySize(width: width, height: height)
        else { throw Refused() }
        awaited = size
    }

    func observeReconfigurationEnd(_ handler: @escaping @MainActor () -> Void) -> AnyObject {
        source.screen.observeFrames { [weak self] size in
            guard let self, awaited == size else { return }
            awaited = nil
            handler()
        }
    }
}
````

````
Make a machine on the custom GPU follow its window, and tell the guest each resize

A Linux machine follows its window by asking its display for the size of the
view; the display of the custom GPU is now an adapter the same policy drives.
A request goes to the device, which answers the guest's next display-information
request with the new size and writes the configuration space to tell the guest.
The display reports the size of the picture the guest last drew, not the size
asked for, and the end of a resize is the first picture of the asked size, so a
guest that never draws at it is reported as ignoring the request and asked
again, as with the framework's display. A size the device cannot report is
refused.

The display event is now written cleared and then set for every resize, so each
write after the first differs from the one before it: the guest's write that
clears the event never reaches the host, and a second update with the same bytes
might not interrupt the guest again. Whether a second resize reaches a running
guest is left to a run against one. The device's resize request is synchronous
now, as the policy needs a refusal at once; the framework's update runs in a
task and a failure of it is logged once.
````
