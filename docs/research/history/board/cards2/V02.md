**Risky: file I/O on a path inside the machine's folder.** Read the patch's `ContainerOutputFile.swift` before applying.

Why: the first real run could not confirm that the container ran `uname`: its output lives only in the app's window, and an
app that was never activated shows no window to automation. A file the next run (and the control service, next card) can
read closes that gap.

Decisions:
- `VMBundle.containerOutput` = `container-output.log`, `previousContainerOutput` = `container-output.1.log`,
  `discardContainerOutput()`.
- New `Engine/Container/ContainerOutputFile.swift` (`final class ContainerOutputFile: Sendable`):
  - `append(_:)` never blocks on the disk: bytes go into a `Mutex`-held buffer and one drain is scheduled on ONE serial
    queue shared by every instance (so two runs of one machine never race on rotation); the queue is injectable for tests.
  - Past the pending limit (1 MiB) new appends are dropped and counted; the batch is first cut to leave room, so the note
    `[dropped N bytes: the disk was slower than the container]` survives the default limits.
  - A drain opens, writes everything (partial writes, EINTR), and closes: no descriptor outlives a drain or a `tail`.
  - Opens use `O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK` (a FIFO at the path neither blocks the writer nor a reader); an existing
    file must pass `fstat`: regular, owned by this user, one link, mode closed to others; otherwise refused and left as it
    is. A missing file is created with `O_EXCL`, then `fchmod` 0600.
  - Rotation: when the file would pass 1 MiB, `rename` current over previous (a link at previous is replaced, not
    followed), then create current exclusively. One drain bigger than the limit keeps its last bytes from a UTF-8 boundary.
  - Each refusal or failure kind is logged once per file object (`Log.container.error`, no path).
  - `tail(current:previous:limit:)` reads at most the last `limit` bytes of previous then current (current opened first; a
    previous with the same inode as current is dropped), cut forward to a character, with a truncated flag; missing or
    refused files read as empty. Not main-actor isolated.
- `ContainerLog(limit:file:)`: with a file, it appends `[run started <ISO 8601>]` at init, the SAME displayable bytes it
  adds to `output`, and lines for the container's exit, the runner's finish and runner errors (filtered). The runner's own
  diagnostics are not written.
- `ContainerMachineFactory.prepare` gives each run `ContainerLog(file: ContainerOutputFile(bundle: bundle))`.
- `VMLibrary.duplicate` discards the copied output in the staged bundle; `delete` removes it with the bundle.
- Help `.containers`: the Output bullet names the file, its mode and size, and that Duplicate does not copy it.

**One existing test changes, on purpose:** `ContainerMachineRunTests.aContainerMachineStartsShowsItsLogAndStopsOnRequest`
(`Tests/VMRunnerTests/ContainerWorkloadTests.swift`) listed the bundle's files as `["config.json", "container-scratch"]`;
the bundle now also holds the output file, so the test waits for the drain and expects
`["config.json", "container-output.log", "container-scratch"]`. Nothing it checked before is dropped. Any OTHER existing
test that fails is a STOP.

New tests: in `ContainerOutputFileTests.swift` (file rules, rotation, links, open file, second link, limits, dropped note
under the default limits, two runs at once across a rotation, append order, FIFO for writer and reader, tail limits and
boundaries, huge sparse file, refused file, the log's filtered text and markers), in `ContainerMachineTests.swift`
(`aContainerMachinesOutputFilesGoWithItsBundle`, `duplicatingAContainerMachineDoesNotCopyItsOutput`) and in
`ContainerWorkloadTests.swift` (`aContainerRunLeavesItsFilteredOutputInTheMachinesFolder`).
