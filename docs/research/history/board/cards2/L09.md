```
## Built so far (2026-10-23): the seed attached to a Linux machine, experimental

The app links `Sources/GuestSeed`. Every part is tested on the host; none of it has run in a guest, so the help says
"experimental".

- **The setting.** A Linux machine has a provisioning spec path: absolute, at most 1024 bytes, checked where the
  configuration is read, approved like the installer image (one read-only approval, which covers the script files below the
  spec's folder). It is in use only while the installer is not attached, since an installer's live system would run the
  steps too.
- **At each start** the app reads the spec (a regular file, 64 KiB at most), checks its script files against their SHA-256,
  compiles the seed with the machine's identifier as the instance identifier, and writes it into the machine's bundle
  (`ProvisioningSeed.iso`, readable by its owner only). A spec that cannot be used stops the start with its line. The seed
  is attached as a read-only USB mass storage device after the disks, and removed with the run's other leftovers when the
  machine stops; a disposable machine gets a new one at each start, like every machine.
- **Saved state.** A suspended machine resumes only with the seed it was saved with. An edit that adds, removes or moves the
  spec drops the saved state, and so does a seed whose contents changed: the digest of the last seed is kept in the bundle
  (`ProvisioningSeed.sha256`). The machine then boots afresh.
- **Posture.** The Isolated and Hardened profiles remove the spec; the exposure summary lists it while it is in use; the
  managed key `AllowProvisioning` removes it from every machine and locks the chooser.
- **Editor and help.** A *Provisioning (experimental)* section chooses, checks and removes the spec; the check lists each
  step with its line, phase and digest, or the refusal with its line. The help topic is marked experimental.
- **USB, not virtio.** cloud-init finds the volume by its label on any block device; USB is what ADR-0012 decided, the bus
  the app already boots installers from, and the device that can later be detached while the machine runs. A guest kernel
  without USB storage would not see it: the first guest run says.

## Remaining

Each item needs a real guest run before its help may drop "experimental".

1. The first real-guest run with a cloud image: that cloud-init finds the read-only USB volume and its Joliet names, runs
   `bootcmd`, `runcmd` and the per-boot script from `/var/lib/cloud/vmrunner`, finds `base64`, and merges the two-part
   document. If the image's kernel has no USB storage, the seed moves to a read-only virtio disk. Detaching the seed after
   the first boot is not built.
2. Installer seed media, one distribution at a time: `OEMDRV` for the Fedora family and openSUSE, `cidata` plus the
   `autoinstall` prompt for Ubuntu, a repacked ISO for Debian preseed.
3. The vsock agent: `ready` and `pre-shutdown`, steps run as the user, secrets delivered at run time (a secret never goes
   into the seed), the guest-side re-check of each script's SHA-256, and Ignition on vsock port 1024.
```

```
# Diary — 2026-10-23 (3)

## Provisioning, second step: the seed attached to a Linux machine

The app now links the provisioning library and builds a Linux machine's cloud-init seed at each start, in a series of
commits that each passed `swift run vmr check`. Nothing here was run with a real guest or in the app's window: every claim
below comes from tests on the host, which build configurations and write files but start no machine.

| # | Claim | Probe | Verdict |
|---|---|---|---|
| 1 | The spec path is stored with a tolerant decode, refused when relative or longer than 1024 bytes, in use only for Linux without the installer, and approved read-only | `ProvisioningSpecPathTests` | TESTED |
| 2 | Isolated and Hardened remove the spec; a spec chosen again reads as Custom; the exposure summary lists it while it is in use | `ProvisioningPostureTests`, `SecurityTests` | TESTED |
| 3 | A start writes the seed into the bundle, 0400, an ISO 9660 volume, the same bytes for the same spec | `ProvisioningSeedTests` | TESTED |
| 4 | A spec or script that cannot be used stops the start with the spec's name and line | `ProvisioningSeedTests` (lines 7 and 11 of the fixture) | TESTED |
| 5 | The seed is attached as a read-only USB drive after the disks, never with the installer, and a missing seed fails the build | `StorageDevicesTests`, `ProvisioningSeedTests` | TESTED |
| 6 | The seed is removed with the run's leftovers; its digest stays | `ProvisioningSeedTests` | TESTED |
| 7 | A saved state is dropped when the seed is added, changed or removed, and kept otherwise | `StorageDevicesTests`, `ProvisioningSeedTests` | TESTED |
| 8 | `AllowProvisioning` clears every machine's spec and locks the chooser | `ManagedPreferencesTests` | TESTED |
| 9 | The help topic says experimental, what the guest can read and what removes the spec | `ProvisioningHelpTests`, `HelpCatalogTests` | TESTED |
| 10 | The editor's check lists each step with its line and digest, or the refusal | `ProvisioningSeedTests` | TESTED |
| 11 | A guest finds the seed and runs its steps | a real-guest run | NOT RUN |

### Decisions

- **USB mass storage, read-only**, as ADR-0012 decided, not a virtio disk: cloud-init finds the volume by its label on any
  bus; USB is the bus the app already boots installers from and the device that can be detached while the machine runs.
- **Not while the installer is attached**: an installer's live system would run the steps too.
- **The seed is built in the machine factory**, before the configuration that attaches it: the controller's class is at
  its length limit, and the factory runs after the disposable copy, which clears the run's leftovers.
- **A saved state needs the same seed**: the digest of the last seed is kept in the bundle, and a different one drops the
  saved state instead of letting a restore run with a drive that changed under the guest.
- **A managed key**, `AllowProvisioning`, beside the keys for the other channels into a guest.
- **The editor's check is a preview**: the start reads the spec and its scripts again and decides.

### Not verified

- That cloud-init in a guest finds the `cidata` volume on a read-only USB drive, reads its Joliet names, runs `bootcmd`,
  `runcmd` and the per-boot script from `/var/lib/cloud/vmrunner`, finds `base64`, and merges the two-part document.
- That a cloud image's kernel has USB storage; a trimmed cloud kernel may not.
- That a machine with the seed attached can still be suspended (the framework decides whether a USB drive can be saved).
- The editor section in the app's window; no screenshot was taken.
- That a start shows the refusal in the window as the tests show it in the error's text.

The chain ran in a worktree of its own; removing it after the merge is the integrator's step.
```
