# Diary — 2026-10-23 (6)

## Third real-guest run: the app's own seed read over virtio, merged and run

One real-guest run was made today, under the owner's authorisation, against a scratch data folder, with the guest capped at
2 CPUs and 2048 MiB, a runtime limit of 15 minutes and no installer attached. The machine's bundle was written by hand, and
the app was started with its own `--start` argument. Accessibility was used only to read the app's window on its own
process: no keystroke, no click, no activation and no screenshot. Everything the run created was removed afterwards.

The guest was a Debian 13 generic arm64 cloud image. Its download size and SHA-512 were checked against the vendor's sums;
no signature was checked. The seed was the app's own, attached as a read-only virtio disk. It is the first run in which a
guest read the app's own seed, and it is one image of one distribution.

### Defects the run found

- **A 3 GiB raw disk is accepted for a 16 GiB machine** with no refusal and no mismatch reported at start. This is the third
  run in which it happened.
- **The exposure disclosure cannot be expanded through Accessibility.** This is the same defect as in the first run; it was
  not retried in this one.

### Why the help topic stays experimental

The help topic *Provisioning (experimental)* stays marked experimental. The run covers one image of one distribution, and
suspend with the seed attached was not observed. Both are needed before the topic can drop the word.

### Not verified

- Cloud images of other distributions, and any image other than this Debian 13 generic arm64 one.
- Suspend with the seed attached, and what happens to the saved state.
- The exposure line for provisioning, in the window.
- The guest's own power-off line; the stop is inferred from the state after the run.
- Installer seed media: no installer was attached in this run.
