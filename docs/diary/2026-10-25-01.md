# Diary — 2026-10-25 (1)

## A virtio GPU implemented by the host, built and tested without a guest

Seven commits (an eighth documents them) build a feasibility study of roadmap 0014's open question, ADR-0014 item 3: can a GPU device implemented by
the host, through the custom virtio devices of macOS 27, drive a Linux guest's display? It lives in `Packages/VirtioGPU`,
which the app neither links nor bundles. Each commit was gated before it was made (8/8). No virtual machine was started:
everything below comes from the 27.0 SDK's headers, from compiling against them, from tests on the host, and from
`--dry-run`, which validates a configuration and starts nothing.

| # | Claim | Probe | Verdict |
|---|---|---|---|
| 1 | The package stays out of the app | a layering test on the root manifest and every root source; `vmr build-app` builds the root product only | TESTED |
| 2 | The framework accepts one custom device with device ID 16, a display class, two queues, version 1 and a 16-byte configuration space | `--dry-run` on macOS 27.0.1, binary signed with the virtualization entitlement | TESTED (validation only) |
| 3 | Without the virtualization entitlement the configuration is refused | `--dry-run` unsigned: `VZErrorDomain` code 2 | TESTED |
| 4 | A serial port's output cannot be `FileHandle.nullDevice` | the framework raised an exception on it; an opened `/dev/null` is accepted | TESTED |
| 5 | Every guest length, count and offset is checked before anything is allocated or copied, and a failed operation changes nothing | table-driven and seeded random hostile requests against the decoder, the store and the device state | TESTED |
| 6 | Each element is read once, answered only when the answer fits, and given back exactly once | the wiring's code; it needs a guest | NOT RUN |
| 7 | The guest finds the device, binds its driver and draws a console on the scanout | the authorised real-guest run | NOT RUN |
| 8 | Giving an element back, or a change of the configuration space, notifies the guest | the headers name no other host-to-guest signal; the run's command record answers it | NOT RUN |
| 9 | The PNG writer writes a private file in place, at most once a second, the newest picture last | the writer compiled with the library outside the runner, on an 8 × 4 picture, when the change was written | TESTED (outside the runner) |

### What was built

- The machine: EFI boot from a raw disk, a read-only seed disk, entropy, a serial console to `console.log`, no network, no
  keyboard or pointer, none of the framework's graphics devices, the custom GPU; caps of 2 CPUs, 2048 MiB and an hour.
- The two-dimensional command set (display information, resources, backing, transfers, scanout, flush, cursor), the
  resource store under limits, the device state, and a bounded record of the requests written to `commands.log`.
- `--probe-config-change` sets the display event in the configuration space; `--headless-dump` writes `scanout.png`;
  `--window` shows the scanout in the runner's own window.

### Decisions to confirm

The defaults the owner may change: the package and target names (ADR-0042: no planning word); PCI subclass 0x80, not VGA;
no optional feature (no EDID, so the guest is not expected to ask for it); one display of 1280 × 800; the limits of 256
resources, 64 MiB each and 256 MiB in all; the seed as a read-only virtio disk; no network for the guest; everything on the
main queue; no signing command in the tooling (the run signs the binary by hand with the virtualization entitlement only).

### Not verified

- Anything a guest does with the device: enumeration, the driver binding, the first commands, the picture, the timings.
- Whether `returnToQueue` notifies the guest; the headers show no method that raises an interrupt.
- Memory mappings at 16 KiB granularity against a guest's 4 KiB pages: the store reads guest memory piece by piece, as
  the guest lists it, and has not met a real backing list.
- The window: built, never opened.
