# Diary — 2026-10-26 (3)

## Continue investigating Windows boot

The owner asked to fix Windows boot, not merely contain the helper crash. TPM work stayed paused. The [boot-display study](../research/windows-boot-display-2026-10.md) records six disposable real-guest probes, their limitations, the newly measured firmware behaviour and the next owner-observed test.

The reported booting implementation also enables fine-grained trap emulation. Its Boolean selector contract was verified without a VM, then paired with PMU in a standalone scratch runner. The pair alone reproduced the original early memory-protection fault. A no-installer control stopped normally.

A separate, independently written EFI diagnostic installed a real RAM-backed graphics output protocol and chainloaded the supplied media's EFI entry. Persistent diagnostic checkpoints established that these steps ran. The child returned EFI_TIMEOUT. An EFI application cannot safely unload while protocols and timer callbacks still point into it; correcting that lifetime let two longer diagnostics stay running until their host stops. This is **not** a verified Windows boot and does not establish the original app had that EFI lifetime bug.

The exposed installer filesystem's root listed only `EFI`, so direct boot-manager/no-prompt paths could not be loaded there. A retry variant was prepared and compiled, without generating input, but not run. The next useful step needs the owner at the window to report what is actually shown and optionally press a key if the media asks. No keys were generated, no screen was captured, and no Setup requirement was altered.
