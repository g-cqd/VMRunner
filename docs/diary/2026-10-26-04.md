## Owner-observed Windows startup and storage

The [Setup/storage study](../research/windows-setup-storage-2026-10.md) records the follow-up to the EFI timeout diagnostics. The owner saw the Windows logo, then reported installation starting with poor responsiveness and no target disk. An in-memory host RAM framebuffer mirror continued displaying Windows after EFI boot-services forwarding ended. Polling was increased to a target 15 Hz, not a measured 15 fps or accelerated display.

The scratch target changed from NVMe to Virtio block, with a verified ARM64 viostor package on a separate read-only driver medium. Initial owner observations suggested incompatibility, but later unfiltered PCI enumeration showed `1AF4:1042`, SCSIAdapter, **Started**, `oem0.inf`. The owner's DiskPart screenshot then showed **Disk 3 Online, 64 GB, 64 GB free**. The storage path therefore works in this experiment. Its exact driver-loading mechanism/timing and Setup's refreshed drive list remain unverified. No installation completed.

Other problem-code-28 devices, including the display and diagnostic observer, do not negate the started storage controller. Windows has no accelerated graphics driver in this test. TPM remains paused; no hardware check or installer file was altered. Owner input/screenshots supplied the guest evidence; the agent generated neither input nor captures and did not force-load a driver.

Before/after ISO hashes/stat records and normal preference stat records match. The brief empty integration-cache directory was also removed. All copied text/metadata files were compared byte-for-byte with their originals, then the five small observation-note directories were removed. The owner's pre-existing `.vscode/` is untouched.

No production source changed, and the known-unsafe PMU guard remains intact. Production boot/display integration requires its own capability decision, lifecycle/memory review and regression coverage; a visible scratch target is not a claim that the app is fixed or Windows can complete installation.
