# Diary — 2026-10-23 (5)

## Real-guest runs of the provisioning seed, and the seed moved to a virtio disk

Two real-guest runs were made today, under the owner's authorisation, against a scratch data folder, with the guest capped at
2 CPUs and 2048 MiB and a runtime limit of 15 minutes. They are the first evidence that a guest reads the seed at all. The
first run used a build of `main` that attached the seed as USB; the second used a later `main`. Both were driven through the
app's own window by Accessibility on its own process, or started by its `--start` argument, with no keystroke, no click and
no capture of anything but the app's window. Everything the runs created was removed afterwards.

The first run showed no sign that cloud-init applied the USB seed, and the second showed that cloud-init found a seed on a
read-only virtio disk. The seed is therefore now attached as a read-only virtio disk, after the disks and
never with the installer (ADR-0012 and roadmap 0016 say so). That change is tested on the host only: no guest has yet run
the app's own seed on virtio.

The first run was built from `main` with the USB attachment; the second from a later `main`, also with USB. The change to
virtio followed the second run. Its tests (`StorageDevicesTests`, `ProvisioningSeedTests`) build the configuration and open
the image files; they start no machine.

### Defects the runs found

- **A raw disk is accepted as the installer image** with no warning (first run). The sheet could say that a file does not
  look like an ISO when it is partitioned.
- **A 3 GiB disk file is accepted for a 16 GiB machine** with no refusal, in both runs. The mismatch was not reported at
  start.
- **The file picker cannot reach hidden folders** such as `/tmp` without a keystroke, and no path field takes a path, so an
  operator without a keyboard cannot choose a file outside the visible folders.
- **The exposure disclosure cannot be expanded through Accessibility.** Its only exposed action is the help popover, so
  assistive technology cannot open the list either.
- **The open panel wrote to the app's preferences domain** in the first run, although the data folder was overridden. The
  panel's own keys (`NSNavPanelExpandedSizeForOpenMode`, `NSOSPLastRootDirectory`) were added. The second run avoided the
  panel: the machine bundle was written by hand, and the preferences file kept its size and modification time.
- **The nocloud image stops at `systemd-firstboot`** on the graphical console and gives no serial login. Shut Down was not
  handled by the guest in that state; Force Stop was needed.
- **The app process exited by itself** about three minutes after the stop in the first run. Not reproduced in the second
  run, where the process stayed alive; not diagnosed.

### Not verified

- That cloud-init reads the app's own seed on the virtio disk, as it read the `hdiutil` ISO.
- That Linux reads the app's Joliet names (`meta-data`, `user-data`), and the `Merge-Type` merge of the two parts.
- That the per-boot script runs from `/var/lib/cloud/vmrunner` as root without `noexec`, and that `base64` exists on the image.
- That the seed attached as a USB drive alone fails for the cause given; the ordering is inferred.
- That a machine with the seed attached can be suspended, and what happens to the saved state.
- That the exposure line for provisioning reads as the source says, in the window (the disclosure could not be expanded).
- That the tarball's signature is valid (only its SHA-512 was checked).
- The nocloud image beyond `systemd-firstboot`, and the app's exit in the first run.
