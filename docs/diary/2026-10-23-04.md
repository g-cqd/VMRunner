# Diary — 2026-10-23 (4)

## The control service from a terminal and from an MCP client

Eight commits (seven of code and tests, one of documentation) add a command-line client of the control service to the
tooling, `vmr control`, and an MCP server over stdio, `vmr control mcp`, which an AI agent launches; each passed
`swift run vmr check`. Nothing here ran against the app, with an MCP client application, or with a real machine: every
claim below comes from tests against the library's own service on sockets under `/tmp`, with machines held in memory.

| # | Claim | Probe | Verdict |
|---|---|---|---|
| 1 | The client keeps an answer that arrives in the same read as the one before, so requests can be sent ahead | two answers in one write; two requests sent before reading | TESTED |
| 2 | An answer nested deeper than 8 levels, or longer than the client accepts, is refused unparsed | client tests over a socket pair | TESTED |
| 3 | A caller sends nothing to a socket another user serves | caller test with the user check injected | TESTED |
| 4 | `vmr control` takes the socket from `--socket`, `VMRUNNER_DATA_DIR` or the default, and the token from a private file or `VMR_CONTROL_TOKEN`, never from an argument | unit tests; the real binary refuses `--token` | TESTED |
| 5 | A token file other users may read or write is refused before anything is sent | unit and end-to-end tests | TESTED |
| 6 | status, list, state, start and stop print what they document and exit 0, 1, 64, 69 or 77 as documented | the real binary against the library's service | TESTED |
| 7 | The MCP server answers initialize, ping and tools/list, refuses malformed messages, and makes each tool call one call of its control method, a refusal a tool error with its code | library tests; a session piped into the real `vmr control mcp` | TESTED |
| 8 | The app's service answers `vmr control`, and an MCP client application can use `vmr control mcp` | the owner's run | NOT RUN |

### What was built

- The library's client: one buffer across answers, an answer bounded in size and nesting, and a caller that checks the
  socket's user and sends its own token on a fresh connection per call.
- `vmr control status | list | state | start | stop` in the tooling, human output or `--json`, exit statuses in its help
  and in CONTRIBUTING.
- A library target, `AgentBridge`, linked by the tooling and not by the app, and `vmr control mcp`.

### Decisions to confirm

The defaults the owner may change: a token file must be closed to every other user (mode 0600 or
stricter), not only to the world; a machine may be named by its name when the token may also list machines; the MCP
server speaks 2025-11-25 and 2025-06-18; it takes lines of at most 1 MiB and ends the session after a longer one; its
server name is `vmrunner-control`; one connection per call rather than one held open (the service closes an idle
connection after 10 s); `AgentBridge` is a library target of its own with a `public` API; a last line without its newline, at
the end of the input, is not answered.

### Not verified

- No MCP client application was used; the messages follow the specification of 2025-11-25 as read, not a client's
  behaviour.
- Exit statuses 75 (no answer in time) and 76 (an answer the client cannot read) are mapped but no end-to-end test reaches
  them.
- That the app and `vmr control` agree on the default socket path was checked by reading both (`Control/control.sock` in
  the data folder), not by a run.
