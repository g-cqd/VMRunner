Three findings from reading, from one validation of a configuration (a throwaway program, nothing in the repository) and

### The custom virtio device on a macOS platform

The same result as in an earlier run, repeated once now. The program builds a configuration with a macOS platform and one
`VZCustomVirtioDeviceConfiguration` (device ID 16, PCI class 3, subclass 0x80, two queues, no provider), and calls
`validate()` and nothing else. What it took to reach the device check, in the order the framework asks:

1. Unsigned: `VZErrorDomain` code 2, "The process doesn’t have the “com.apple.security.virtualization” entitlement." That is a
   different refusal and says nothing about the device.
2. Signed with only that entitlement, but with no auxiliary storage: code 2, "“auxiliaryStorage” is nil."
3. With a hardware model, a machine identifier, auxiliary storage (a file in the temporary directory, removed after) and the
   macOS boot loader, 2 processors and 4 GiB: the device is refused. The hardware model came from a hand-written property
   list (data representation version 1, minimum OS 14.0.0, platform version 2), which the framework accepted and reported as
   supported; no restore image was used.

The result, verbatim: error domain `VZErrorDomain`, code 2, localized description "Invalid virtual machine configuration.
Custom Virtio devices must be configured with a generic platform." (failure reason: "Custom Virtio devices must be configured
with a generic platform."). A macOS guest can therefore not use the host-implemented GPU or the host-implemented input
devices; the settings and the builder keep that choice to Linux guests, and nothing here changes it.

### The private ROM image selector

On `VZEFIBootLoader`, `class_getInstanceMethod` and `method_getTypeEncoding` find `_setROMImageURL:` with the encoding
`v24@0:8@16` (digits stripped: `v@:@`, one object argument) and `_ROMImageURL` with `@16@0:8`. Nothing was called, so what the
argument must be, what the framework does with the file and whether `validate()` accepts it are unknown. It feeds the design
note `docs/research/windows-framebuffer-shim-2026-10.md`, which is a design only.

### Capturing the machine's picture: decided in part, the rest deferred

- **Decided: a machine on the custom GPU can be captured from the app's data.** The app keeps the newest picture of the
  scanout in `CustomScreen.frame` whether or not a window shows it, so a screen capability of the control service can answer
  from it without a window. It is designed for machines using the custom GPU; the code is a separate change.
- **Deferred: capturing the framework's own view** (macOS guests, and Linux guests on the framework's graphics device) with
  ScreenCaptureKit on the app's own window. Reasons:
  1. The work done without a guest can test the crop arithmetic and nothing else; the capture itself needs a running machine.
  2. It needs an open window, and a registry from a machine to its view: the view exists only while SwiftUI hosts it, and
     full screen replaces it with a new one.
  3. The Screen Recording permission behaviour for a capture of the app's own process on macOS 27 is unverified. The one
     measurement (`docs/research/automation-2026-10.md`, macOS 26.7.1) saw no prompt and says to re-check it on a clean account.
  4. AppKit's `cacheDisplay` of the framework's view returns black (same study), so it is no fallback.
  5. No private selector is used to take a screenshot, and none will be added for this.

### Pixel density for a macOS guest

No gap in the code. The density is the configured `pixelsPerInch`, clamped to its range and passed once, when the machine's
graphics display is built (`ConfigurationBuilder`). With "Resize guest display with window" on, a macOS guest is resized by
the framework's view (`automaticallyReconfiguresDisplay`, set in `VMDisplay.swift`), which the framework documents as
reconfiguring the display to match the host display environment; the app does not resize a macOS guest itself. What is
missing is a check: the window has not been moved between a Retina and a non-Retina display with a macOS guest running. That
step is added to the owner's list in roadmap 0039.
