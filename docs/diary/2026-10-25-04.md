### What was built

- The workload holds an activity while its runner lives, and the process logs the steps of a stop (category `container`).
- Each container machine keeps its output in `container-output.log` and `container-output.1.log` in its folder. A drain on one
  queue shared by all files writes it; the app's main actor never waits for the disk.
- The control service has a read-only method `machines.log` and a capability `log`; the app reads the end of the files off the
  main actor; `vmr control log MACHINE [--bytes N] [--json]` and the fifth MCP tool print or return it. A container's exposure
  summary says so when agent access is on.
- A test that every path of the control listener closes the connection it accepted.

### Not verified

- Whether the activity shortens the stop. Nothing was run with it, and App Nap is a candidate, not a finding.
- Anything on a real guest after these changes: the output file with a real run, the stop with its logs.
- The log lines themselves: no test reads them.
- Why the app's descriptors grew from 44 to 54; the listener is not the explanation the tests can rule in.
- The output in the window and the menu quit, which automation could not reach.
- The placeholder bundle identifier is shared with an installed copy of the app (the defaults and data-directory override
  domains); the run wrote only the override domain. That is an owner decision, not a code defect.
