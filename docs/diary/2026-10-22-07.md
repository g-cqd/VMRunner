## Fixes of the macOS real-guest run, and the run's record

documented. The commits pass `swift run vmr check`, and this entry records the run. The fixes have unit tests with fakes; the run was not repeated, so the fixes are not yet seen in
a guest. The run used a macOS guest with the framework minimum, 2 CPUs and 4096 MiB. The first attempt used a 16 GiB disk and

### Defects found and the fixes

- **The disk minimum.** The new-machine range was 16 GiB for both guests, so a 16 GiB macOS machine could be created and failed.
  macOS now has its own range from 40 GiB, and the disk help says so. A value between 16 and 40 GiB was not tried.
- **A disposable run's address saved into the machine.** A disposable start with a fresh identity wrote its new MAC address into
  the machine's stored configuration, so a later normal start used the address of the last throwaway run. The address of a run
  is now used for that run only; a machine with no stored address is still given one and keeps it.
- **The split view's width saved into the owner's preferences.** After a run with a separate data directory, the standard
  domain's split-view entry for the main window showed the sidebar collapsed, so the owner's next launch could open with the
  sidebar hidden. The split view's autosave is the one writer found; the run did not show it writing. The split views of such
  a run no longer keep an autosave name. The owner's preferences for the app changed once during the run.
- **Where a download's temporary file lives.** The system writes a download to `$TMPDIR` first, outside the data directory, so
  that volume needs as much free space as the image (about 19 GB for macOS). A download killed midway can leave its file
  behind. The app cannot choose that location with a download task, so this is documented, not changed: CONTRIBUTING
  and the restore image help now say so.
