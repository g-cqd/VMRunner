# Diary — 2026-10-25 (2)

## A container is a machine of the app, run by a separate signed runner

Decisions: ADR-0057 accepted, amending ADR-0017 decision 1. Roadmap 0024 and 0036 updated. The study
`docs/research/containers-2026-10.md` gains the list of pins whose licences are still to be read.

Ten commits (an eleventh documents them) turn the container runner of 2026-10-22 into something the app can start, show and
stop. Each was gated before it was made (8/8). No virtual machine was started and the real runner was never run: everything
below comes from tests with fake runner executables (a shell script the test writes), from one real build of the bundle and
from reading it with `codesign`.

### What was decided, and why

- **A separate process, not a link.** The container package brings 28 others, 29 pins in all, and their licences have not been
  read. Linking them would put all of that into the process that holds the user's machines and change ADR-0001's account of
  the app. The runner already existed, signed, with its own lock file, and what the app needs from it is one run with a
  beginning and an end. So the app drives it over a command line, JSON event lines and a stop line (ADR-0057). Linking is not
  ruled out; it waits for the licence inventory and an access review.
- **A stop is a line, and standard input closing is also a stop.** A runner whose app died cannot be told anything, but it can
  see its input end. This is how an orphaned runner ends, and the app's own quit hook only has to be faster than that.
- **The log is bounded and filtered because the container is untrusted.** The runner reports chunks of at most 16 KiB; the app
  keeps 1 MiB, drops the oldest and says how much, and nothing reaches the screen except through the console filter.
- **The costs are written down** in ADR-0057: a 79 MB debug runner in the bundle, a longer `build-app`, an extra unsandboxed
  process with the virtualization entitlement, and a kernel and image cache for every container machine.
- **Nothing else was decided.** The user-mode stack in a container, image cache management and a sandbox for the runner stay
  open.

### What went wrong

Roadmap 0036 still listed the container first run as waiting for the owner, three days after it was done, and the study said
the library brought 24 packages where the lock file holds 28 besides the package itself. Both are corrected. The white paper
still says "in time, containers"; it was not touched.

### Decisions to confirm

The defaults the owner may change: ten seconds before SIGTERM and five more before SIGKILL; 1 MiB of log; the network choices
`none` and `loopback` only; the scratch folder inside the machine's bundle, so each container machine downloads its own kernel;
the runner in the bundle in every build, not only in release; the managed key `AllowContainers`.

### Not verified

- A container started from the app, with a real guest: the log, the stop, the quit with a runner alive, the descriptors and the
  processes left behind.
- The size of the release runner, and the time of a cold `build-app` in release.
- That the runner behaves under App Sandbox or a Seatbelt profile.
- The licences of the 28 packages the library brings in; the study lists them by name and version and claims none.

### Next

The authorised run of a container machine from the app, then the user-mode stack in a container, then the management of the
image cache. The licence inventory comes before any linking.

### Cleanup

The tests use scratch folders under the temporary directory and start no virtual machine; they were removed by the tests. The
one real build of the bundle was made in the chain's worktree, in its git-ignored build folder, which was not removed.
